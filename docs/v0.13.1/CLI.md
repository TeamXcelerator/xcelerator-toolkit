# Xcelerator Toolkit v0.13.1 Command Line

The workspace now builds a real `xc` binary from `xc-cli`:

```powershell
cargo build -p xc-cli
target\debug\xc.exe --help
```

All successful operations other than help write a versioned JSON envelope to standard output. Failures write a JSON error with a stable category to standard error. Each error embeds a versioned `FailureDiagnostic` containing stage, operation, optional problem and artifact identities, source cause, optional saved-diagnostic path, resource and authority context, retry classification, and whether higher precision is a reasonable retry. Request loading identifies the exact document path. Unknown fields in request documents are rejected.

## Implemented cache commands

```text
xc cache auth-probe OWNER/REPOSITORY
xc cache package REQUEST.json
xc cache reconstruct REQUEST.json
xc cache verify-package REQUEST.json
xc cache transaction JOURNAL_ROOT TRANSACTION_ID
xc cache find REQUEST.json
xc cache inspect REQUEST.json
xc cache validate REQUEST.json
xc cache shard-status REQUEST.json
xc cache revoke REQUEST.json
xc cache supersede REQUEST.json
xc cache rollover REQUEST.json
xc cache fetch REQUEST.json
xc cache audit REQUEST.json
xc cache prune REQUEST.json
xc cache plan REQUEST.json
xc cache placement-plan REQUEST.json
xc cache dedup-plan REQUEST.json
xc cache export REQUEST.json
xc cache verify-bundle REQUEST.json
xc cache verify-live-acceptance RECORD.json
xc cache consume-bundle REQUEST.json
xc cache publish REQUEST.json
xc cache resume REQUEST.json
xc cache abandon REQUEST.json
```

`auth-probe` asks the configured Git credential provider for GitHub credentials, queries only the allowlisted GitHub user and repository endpoints, verifies effective write permission, and prints redacted evidence. Tokens are never placed in command arguments, environment variables, output, evidence, or diagnostics.

`package` produces an atomically visible deterministic ZIP/ZIP64 package after verifying every source against its canonical payload item. Its request document contains:

```text
schema_version: 1
envelope: CanonicalPayloadEnvelope
sources: [PayloadFileSource]
destination: local path that does not already exist
resources: fully resolved ResourcePolicy
```

`reconstruct` reads only the authoritative ordered parts, verifies every part and the whole-package digest, and atomically exposes the reconstructed package. Its request contains `schema_version`, `encoding`, `parts_root`, `destination`, and `resources`.

`verify-package` verifies the package digest, deterministic encoding metadata, decoded path order, logical sizes, and logical content hashes. Its request contains `schema_version`, `envelope`, `encoding`, `package_path`, and `resources`. The resource policy supplies the cooperative wall-time deadline; verification remains streaming and bounded-memory.

`transaction` loads and verifies the latest append-only checkpoint for a publication transaction before printing it.

`find` accepts a bounded `RemoteSemanticQuery`, ordered private/public overlay descriptions, and read-only Git transport settings. It computes the canonical semantic digest, loads each trusted family topology and only the matching shard-index partition, evaluates partitioned revocations, disposition, minimum assurance, toolkit-reader compatibility, and accepted publication-policy digests, then verifies the canonical manifest, atomic publication receipt, and selected transport record. Exact dependency identities are resolved recursively through their named families within explicit depth/count limits. The result identifies every selected repository/ref/path and all rejected or missing candidates. Metadata lookup does not fetch an `objects/` payload path or create a persistent clone.

The same query may restrict scalar backends, set a positive minimum precision, pin the resolved mathematical configuration, and require exact provenance-evidence digests already bound by the publication receipt. These constraints combine with minimum assurance, accepted policies, disposition, revocation, and toolkit compatibility; a candidate failing any one is reported as rejected before payload retrieval.

`inspect` uses the same bounded semantic query and ordered overlays as `find`, but identifies the operation as an inventory/provenance inspection in its stable output envelope. The complete selected manifest, transport, receipt, repository/ref/path sources, dependency closure, and structured candidate rejections are returned without payload materialization.

`find`, `inspect`, `validate`, and `fetch` return a stable `cache_provenance` record alongside their resolution result. It records the ordered overlays, hit or miss, reuse disposition, exact selected repository/revision/document paths, rejected candidates, and validation outcome. Full validation also lists every dependency identity whose payload was verified. The same record can be appended to library `SolverProvenance`; its duplication audit identifies work recomputed even though an admissible hit was available.

`validate` accepts the same semantic query, overlays, and read-only transport plus a typed `mode`. `fast` performs the complete trusted metadata, policy, compatibility, revocation, manifest, receipt, transport, and dependency-identity proof and forbids payload staging paths; Certified requests cannot use it. `full` additionally requires explicit `parts_root`, root `package_destination`, and `dependency_packages_root`. It traverses the already identity-verified graph dependency-first, selectively downloads or reuses every artifact's manifest-directed parts, reconstructs every exact package, and verifies deterministic ZIP metadata plus every decoded logical path, size, content digest, and canonical payload identity. Duplicate dependencies are materialized once, cycles fail closed, and the report lists the fully validated closure. A full request fails when the artifact does not resolve.

`shard-status` accepts a family, private/public visibility, trusted topology source and anti-rollback policy, endpoint network registry, and bounded read-only transport. It reads one trusted family topology, follows its ordered route, and reports each shard's topology status, repository/ref, and independently validated shard-local capacity ledger. It never reads payload objects or creates a persistent clone.

`revoke` plans or executes one auditable revocation-partition update. Its typed request binds a shard through the network registry, the complete `RevocationRecord`, a partition byte bound, bounded no-checkout Git transport, `execute_remote_mutations`, and `confirm_revocation`. Dry runs require both mutation and confirmation to be false. Execution requires both true, obtains fresh effective write permission for the exact repository, rechecks the head and observed partition digest, performs one compare-and-swap commit, and verifies the committed partition. Identical retries are no-ops; an attempt to rewrite an existing scope/identity record fails. Records retain semantic/payload/manifest/transport/attestation/repository/policy scope, reason, effective time, optional replacement, incident reference, and authorizing-evidence digest.

`supersede` plans or executes one immutable correction edge without rewriting either artifact. Its typed request binds the shard, exact prior and replacement semantic/manifest/payload digests, reason, effective time, authorizing-evidence digest, partition bound, transport, `execute_remote_mutations`, and `confirm_supersession`. Planning requires both manifests to exist at the same exact shard head and match their declared digests. Execution obtains fresh write permission, rechecks the head and observed two-hex-digit supersession partition, performs one compare-and-swap commit, and verifies the committed partition. Identical retries are no-ops and an existing prior semantic/manifest edge cannot be rewritten. The bounded library reader follows these partitions transitively with cycle and depth rejection, while the original identities remain pinned and reproducible.

`rollover` performs the separately reviewed topology transaction that activates an initialized successor shard. Its typed request binds the trusted exact registry, family/visibility route, prior writable shard, complete `SuccessorShardReadinessEvidence`, bounded transport, `execute_remote_mutations`, and `confirm_rollover`. Readiness requires exact ownership/visibility, branch-protection, trust-metadata, read/write-health, and reviewer evidence plus a clean audit of an empty successor at its unchanged head. The initial shard-local ledger must be the remotely present canonical ledger, name that revision, use the 100,000,000,000-byte hard capacity, and have complete history coverage. A dry run produces the generation-linked replacement registry. Confirmed execution obtains fresh registry write authority, rechecks the exact head and registry digest, changes only the prior/successor statuses in one compare-and-swap commit, and verifies the committed topology.

`fetch` accepts the same query, overlays, and bounded read-only transport plus an explicit verified-parts root and package destination. It first performs the complete `find` proof. On a hit, it downloads only missing manifest-directed parts, verifies each part while retaining it for retry/reuse, reconstructs the exact package, and fully validates deterministic ZIP metadata and every decoded logical path, size, and content digest against the self-contained canonical payload envelope. It reports logical bytes, transport bytes, projected new local bytes, origin repository/ref, downloaded and reused parts, and the final verification result. If the package destination already contains the verified artifact, no payload object is fetched. A lookup miss remains a structured successful diagnostic with no materialization.

`audit` is read-only. Its request names an exact repository branch and shard identity, bounded path-enumeration and metadata-read policy, and read-only Git transport settings. The command resolves the current head, enumerates only bounded tree paths, validates every current index entry against its self-contained manifest, transport records, publication receipt, receipt-bound metadata, and named object paths, then reconstructs the complete discoverable index projection. It also validates every append-only payload-batch record, verifies receipt-bound record digests, reconstructs exact first-seen payload bytes when every reachable object has consistent history coverage, and compares that result with completed-plus-abandoned ledger bytes. It reports coverage gaps, logical and backend-local unique bytes, ledger coverage and remaining capacity, incomplete transactions, missing records or objects, projection drift, and reachable unreferenced manifests, encodings, receipts, and objects. Ordinary audit never downloads payload blobs and never guesses reclaimed capacity when durable history is incomplete.

`repair-index` runs the same bounded read-only audit and derives a canonical repair plan only for index partitions that the audit proved drifted. Its request binds the shard to an enabled GitHub network-registry endpoint, sets independent audit and repair file/byte bounds, and explicitly states whether entry removal or repair in the presence of unresolved integrity errors is allowed. It is a dry run unless both `execute_remote_mutations` and `confirm_repair` are `true`. Mutation obtains fresh effective GitHub write permission for the exact endpoint, stages only canonical reconstructed partitions, rechecks every observed index digest and the branch head, makes one compare-and-swap commit, and verifies every replacement at the accepted commit. A ref conflict returns without retrying against an unreviewed plan. This command does not rewrite the capacity ledger; ledger repair remains conservative until all required payload and metadata accounting components are provable.

`prune` supports either an unconfirmed dry run or an explicitly confirmed local deletion. Its typed request supplies the exact regular non-symlink file path, expected file length and SHA-256, local candidate, prune policy, family durability policy, independently verified copy evidence, and resource policy. Both modes evaluate age, project pins, dependency reachability, active transactions, assurance, disposition, recomputation cost, every required publication target's receipt-complete state, accepted copy locations, distinct failure domains, revocation, and any required archive copy. Execution recomputes that complete plan immediately before deletion, streams and verifies the exact file, polls policy-bound cancellation, and refuses changed content. Public/private remote copies are evidence inputs only; remote locations cannot form a valid prune candidate.

`plan` accepts a typed artifact DAG and a complete ordered policy over trust, precision, locality, transfer bytes, recomputation cost, and action preference. Candidates describe load, derive, recompute, or certify routes plus compatibility, revocation, availability, assurance, exact dependencies, and cumulative resource costs. The deterministic result gives dependency-first execution order, the selected route for every satisfiable node, total projected costs, and explicit rejection reasons for every alternative or unresolved node. It performs no computation, retrieval, or mutation.

`placement-plan` is a nonmutating storage and transfer preflight. Every candidate reports logical bytes, backend-local unique added bytes, transfer bytes, destination, retention class, availability, operational suitability, and a digest-bound currency/storage/transfer estimate. Policy applies explicit unique-byte and transfer quotas plus allowed retention. GitHub public/private candidates remain first while free and suitable. A paid backend is inadmissible without approval bound to its exact backend, estimate, governance policy, approver, cost ceilings, justification, and evidence; it cannot displace a suitable GitHub candidate unless that approval explicitly authorizes the override. Output displays every estimate, selected destination, policy outcome, and rejection reason.

`dedup-plan` is nonmutating and consumes only inventories already authorized and observed by the caller; it performs no repository discovery. Its report separately accounts for logical canonical-payload reuse, physical object reuse inside the exact target repository, objects that still require a cross-repository copy, and new uploads. A public request fails closed if the target, any object inventory, or any logical observation is private/local/team scoped, so public output cannot reveal whether a matching private-only object exists. Physical deduplication is never claimed across distinct GitHub repositories.

`export` creates an atomically visible portable directory bundle from an explicitly declared root set and its exact dependency-complete artifact records. Each source names an already materialized verified-parts root, self-contained canonical manifest, transport record, assurance, disposition, and optional origin receipt. Export rejects missing dependencies, conflicting part paths, identity drift, unsafe paths, corrupt bytes, and resource-limit overflow; streams rather than buffering payloads; preserves original transport identities; and writes canonical `bundle.json` metadata plus original manifest-directed paths under `parts/`. Full policy mode reconstructs and validates every decoded ZIP payload before the bundle becomes visible.

`verify-bundle` is network-free. It bounds and canonicalizes bundle metadata, validates the exact dependency closure and optional receipt bindings, verifies every stored part and whole-package digest, and, in full mode, reconstructs each artifact in an explicit scratch root outside the immutable bundle and verifies decoded paths, sizes, hashes, ZIP metadata, and canonical payload identity. Its report distinguishes artifact roots, part references, stored paths, referenced package bytes, stored bytes, and decoded artifacts.

`verify-live-acceptance` is also network-free and never mutates GitHub. It accepts a tagged `publication` or `large_corpus` record. Publication verification requires owner-direct private, public, and dual receipts, a contributor-reviewed public receipt, common validation evidence, public sanitization evidence, remote commit verification, zero persistent full-clone storage, and an unchanged-ref no-mutation control. Large-corpus verification replays the topology-only registry, every shard observation, selective decoded retrieval, capacity/rollover decision, sub-100-MB parts, at-most-1-GB batches, remote payload and receipt checks, and zero persistent full-clone storage. Both record types bind the source revision and complete evidence with canonical SHA-256. A valid simulated scale report cannot be relabelled as live evidence because the live wrapper requires an independent GitHub measurement digest and `measured_on_live_github=true`.

`consume-bundle` verifies bundle metadata and transport bytes, enforces reader-version, minimum-assurance, disposition, and exact dependency-closure policy, then reconstructs and fully validates one exact artifact to an absent destination. Quarantined or revoked artifacts are never consumable; deprecated artifacts require explicit policy. It performs no network access and removes a newly materialized package if decoded verification fails.

`publish` is dry-run unless `execute_remote_mutations` is exactly `true`. Its typed request binds the artifact family and private/public/both target to the resolved publication policy, a trusted remote topology source, anti-rollback trust policy, endpoint network registry, deterministic transport encoding and hard transport limits, target-specific candidate/authority/review inputs, append-only journal root, and bounded no-checkout Git transport. Discovery reads only the current top-level family-routing document and the small capacity ledger at the exact head of each writable candidate shard. It selects the fullest admissible shard, probes fresh effective GitHub write permission for the selected repository, applies owner-direct or contributor policy, and emits the complete routing and coordinated transaction plan without changing a remote repository.

Remote `find`, `inspect`, `validate`, `fetch`, `publish`, and `resume` requests include explicit fabric trust roots. Each root binds repository owner/name, branch, an exact head or digest-bound ancestry statement, current digest-bound branch-protection evidence, approved trust anchor, and approved publication policy. Publication additionally supplies the evaluation time used to reject expired protection evidence. An internally consistent but untrusted repository, rewritten head, stale protection statement, or unapproved policy fails before acceptance or mutation.

A mutating `publish` additionally requires the staging/resource/step-limited `execution` block and exact target metadata bundles. The execution staging root and resolved resource policy must exactly match the Git transport staging root and resource policy, preventing validation and mutation from operating on different files or limits. Candidate identities, validator evidence, target metadata, assurance, disposition, manifest, and transport must match those bundles before the first checkpoint. The command creates or resumes the stable idempotency journal and advances it through bounded compare-and-swap payload commits. After independently verifying each accepted payload commit, it stages, commits, and verifies a separate small canonical batch record; the record is never added to a potentially full 1,000,000,000-byte payload commit. Capacity is rechecked before both mutations, and receipts bind the verified batch-record paths and digests. Re-running the same request loads existing progress instead of replacing it with a new planned journal.

`resume` always loads and verifies the latest journal checkpoint. The minimal read-only request contains `schema_version`, `journal_root`, `transaction_id`, `execute_remote_mutations: false`, and no `transport`, `route_guard`, or `execution` block; it reports the exact next phase, verified-batch progress, newly committed bytes, and reachable commits for every target.

A mutating resume must instead set `execute_remote_mutations: true` and supply complete `transport`, `route_guard`, and `execution` blocks. The route guard contains the artifact family, resolved publication policy, current trusted topology source/policy, and endpoint registry. Before every step, the command rechecks that each incomplete journal shard is still the current writable family endpoint and that topology, journal, and supplied publication-policy digests agree. The execution block supplies a staging root and resolved resource policy that must exactly match the Git transport, a bounded step count, and one target configuration for every incomplete target. Each target configuration supplies the finalization policy, target-specific metadata bundle, maximum index-read bytes, and stable receipt verification timestamp. The public sanitizer is taken only from the digest-bound publication policy; it cannot be replaced in an execution request. The command also obtains fresh GitHub permission evidence, advances only journaled work, checkpoints every accepted state transition, and stops durably at the configured step limit or when every target is receipt-complete or abandoned. It never reads a token from the request document.

`abandon` requires a typed request with `schema_version`, journal locator, one destination, a reason, `confirm_abandon: true`, and bounded Git transport settings. It obtains fresh write-permission evidence and reads the current remote head. Abandonment fails closed if the transaction receipt is present, because that may mean a prior final compare-and-swap succeeded even if its response was lost. A successful append-only checkpoint reports remote bytes and commits that remain reachable for capacity reconciliation. Local staging is reported cleanup-eligible only after every target is receipt-complete or abandoned; cleanup is never implicit.

## Remote mutation boundary

Remote publication is never inferred from credentials. `publish` and `resume` remain nonmutating unless their request explicitly sets `execute_remote_mutations: true`; mutating requests must pass policy, sanitizer, live-route, capacity, authority, resource, idempotency, and document-identity gates. The no-checkout Git path and complete transaction are validated against real local bare repositories. Live GitHub validation is still required before this implementation is considered publication-grade acceptance, so operators should use dry-run plans until the intended registry/shard fixtures and validation procedure are reviewed.
